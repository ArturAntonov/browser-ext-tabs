# Расширение «Поиск по вкладкам» для Яндекс Браузера — план

## 1. Как устроены расширения для Яндекс Браузера

- Яндекс Браузер построен на Chromium (у тебя стоит 26.8.3), поэтому расширения пишутся **как обычные Chrome-расширения на Manifest V3**: `manifest.json` + service worker + popup/side panel, API `chrome.*`.
- Отдельного SDK или публичного кабинета разработчика у Яндекса нет. Встроенный «Каталог дополнений» курирует сам Яндекс, сторонний автор попасть туда не может (максимум — заявка через форму обратной связи, без гарантий).
- Пользователи ставят сторонние расширения из **Chrome Web Store** и **Opera Add-ons**, оба магазина работают в Я.Браузере. Значит, «отправить в магазин» на практике = опубликовать в CWS (основной путь) и/или в Opera Add-ons.
- Для локального теста: `browser://extensions` → «Режим разработчика» → «Загрузить распакованное расширение».

## 2. Главный риск: группы вкладок в Яндексе ≠ группы вкладок в Chrome

В Chrome группа — это цветная метка на вкладках в одной полосе. Для этого есть API `chrome.tabGroups` и поле `tab.groupId`.

В Яндексе группы устроены как **рабочие пространства**:
- в окне есть «вкладки окна» (вне групп) и **активная группа**; другие группы открываются через меню, при этом новая группа **заменяет** крайнюю правую незакреплённую;
- группа хранится независимо от окон, одну группу можно открыть в нескольких окнах сразу;
- группы бывают облачными (синхронизация через Яндекс ID).

Отсюда открытые вопросы, которые из документации не закрыть, только экспериментом:

| Вопрос | Почему важно |
|---|---|
| Есть ли `chrome.tabGroups` и заполнен ли `tab.groupId`? | Без этого нельзя определить «текущую группу» |
| Отдаёт ли `chrome.tabs.query({})` вкладки **неактивных и неоткрытых** групп? | От этого зависит, реальна ли «программа максимум» |
| Совпадает ли название группы из API с названием в интерфейсе Яндекса? | Нужно для фильтра «в какой группе искать» |
| Можно ли активировать вкладку из чужой группы через `chrome.tabs.update` + `chrome.windows.update`? | Нужно для перехода к найденной вкладке |

Скорее всего неоткрытые группы для расширений **не видны** (их вкладки не загружены как табы). Тогда «поиск по всем группам» ограничится группами, открытыми хотя бы в одном окне. Этот сценарий нужно проверить первым делом.

## 3. План разработки

### Этап 0. Разведка API (≈0.5 дня) — делать первым
Мини-расширение-диагностика: popup с кнопкой «Дамп», которая выводит JSON:
- `typeof chrome.tabGroups`, `chrome.tabGroups.query({})`;
- `chrome.tabs.query({})` с полями `id, windowId, groupId, title, url, active, discarded`;
- `chrome.windows.getAll()`.

Прогон в нескольких состояниях: одна группа открыта; две группы в разных окнах; переключились на другую группу; группа закреплена; облачная группа.
**Результат:** таблица «что видно / чего не видно» и решение по объёму MVP.

### Этап 1. MVP: поиск в текущем окне/группе (1–2 дня)
- Manifest V3, разрешения `tabs` (+ `tabGroups`, если оно есть).
- Popup по горячей клавише (`commands`, например `Ctrl+Shift+K`, есть Alt-вариант):
  - поле ввода с фокусом, список вкладок: favicon, title, домен;
  - нечёткий поиск по title + hostname + url (свой простой скоринг или fuse.js);
  - навигация ↑/↓, Enter — переключиться (`tabs.update({active})` + `windows.update({focused})`), Ctrl+Enter / Del — закрыть вкладку.
- Область поиска по умолчанию — текущая группа (по `groupId` активной вкладки), если API её даёт; иначе — текущее окно.

### Этап 2. Программа максимум: выбор области (1–2 дня, зависит от этапа 0)
- Переключатель области: «Текущая группа / Окно / Все открытые».
- Группировка результатов по группам с их названием и цветом.
- Если этап 0 покажет, что неоткрытые группы недоступны, в UI это пишем явно («поиск по открытым группам»). Обходных путей вроде `chrome.sessions` или парсинга профиля не делаем: ненадёжно и не пройдёт ревью магазина.

### Этап 3. Полировка (1 день)
- Side panel (`chrome.sidePanel`) как альтернатива popup — если Я.Браузер его поддерживает (проверить на этапе 0).
- Подсветка совпадений, сортировка по недавности (хранить `lastAccessed` или использовать поле из API).
- Настройки: горячая клавиша, область по умолчанию.
- Тёмная тема, локализация ru/en (`_locales`).

### Этап 4. Тестирование
- Юнит-тесты на поиск и скоринг (vitest), логика отделена от `chrome.*`.
- Ручной чек-лист в Я.Браузере: 200+ вкладок, несколько окон, группы, закреплённые вкладки, `discarded`-вкладки.
- Дополнительно прогнать в Chrome: CWS ревьюит в Chrome, расширение должно там работать.

### Этап 5. Публикация
1. **Chrome Web Store** (основной путь): аккаунт разработчика с разовым взносом $5, иконки 128 px, скриншоты 1280×800, описание, privacy policy (можно короткую страницу на GitHub Pages: «данные не собираются и не передаются»), обоснование каждого разрешения. Ревью обычно занимает от нескольких дней до пары недель. Минимум разрешений (`tabs`, `tabGroups`, без `host_permissions`) ускоряет ревью.
2. **Opera Add-ons** (опционально): бесплатно, тот же пакет, ручное ревью бывает долгим.
3. Яндекс-каталог: только заявка через обратную связь, без гарантий.

## 4. Стек
Ванильный TypeScript + Vite (или `@crxjs/vite-plugin`), без фреймворка: popup маленький, важна скорость открытия. Поиск — свой скоринг или fuse.js.

## 5. Порядок
Этап 0 → решение по объёму → этапы 1 и 4 (параллельно: тесты на поиск) → этап 2 → этап 3 → этап 5.
